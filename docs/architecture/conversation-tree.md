# Conversation tree (prompt-cache navigator)

A pane that replaces the ambient rail while open (`.stage.with-tree`; it shows in the focus layout too, where the rail is hidden). It draws the active tab's conversation as a git-style graph — one row per user prompt, oldest first, branches in their own lanes, a divider per compaction — and for each prompt says whether *re-asking it* (branching just before it) reuses the provider's prompt cache: `warm` (> 10 min left), `expiring` (≤ 10 min), `partial` (cached up to an earlier anchor), `cold`, or `unknown` (no cache lifetime reported: no colours, no prices). Opened and closed by the toolbar's tree button (its refresh button sits beside it while the pane is open), and opened by `/tree` and `/branch` (`handleCommand`; both shadow omp's terminal pickers of the same names).

**Data flow.** `conversation_tree` command (`src-tauri/src/conversation_tree/`: the active file plus its *family* — the connected component of `parentSession` links among the `*.jsonl` files of the **same directory**, ≤ 32 files, subagent sub-folders never join — merged by entry id, because branch/fork copies keep ids; the path is validated against the profile's sessions root; off the async thread) → `app/conversation-tree.js` (`OMP_CONV_TREE.buildModel(tree, { now })`: pure, rows + lanes + tips + prices, regression `test-conversation-tree.mjs`; the tree's shape — the entry index and the lane layout, no cache facts — is `app/conversation-tree-graph.js`, `OMP_CONV_GRAPH.indexTree`/`layout`) → `app/use-conversation-tree.jsx` (refetch on open, tab change, `sessionFile` change — which `get_state` reports after a branch/fork — a run settling (`streaming` drops between the steps of one run, so the refetch waits until it stayed down 1.5 s) and the refresh button; the request carries the hook's own `sessionFile` and `profileId` (`conversationTree(sessionFile, profile)`, like `recentModels`); a 30 s `now` tick re-derives the model without refetching; a result for a tab or file left meanwhile is dropped) → `design/conversation-tree.jsx` (+ `-rows`, `-detail`, `layout/tree.css`).

**Cache model** (measured on omp 18.6.0 with Opus 5.5 unless marked):
- A later turn does **not** refresh older points. The prefix before prompt P is refreshed only by requests that read it: the first request answering P and the first request answering any sibling prompt re-asked from the same parent. So `touch(P) = max(firstReq(S))` over prompts sharing P's `parentId`; cached while `touch + ttl > now`. `cache-warm` `model_usage` entries refresh the tip.
- TTL comes from `usage.cttl` (`ephemeral1h` → 3600 s, `ephemeral5m` → 300 s); absent on non-Anthropic providers → `unknown`. Prices are `cost.cacheRead / cacheRead` and `cost.cacheWrite / cacheWrite` per token.
- Tools + system prompt stay cached while any request of the tab runs within the TTL (≈ the smallest non-zero `cacheRead`, 13,335 tokens in the author's sessions), so a cold re-ask writes only the conversation.
- Anchors (inferred from `packages/ai/src/providers/anthropic.ts` and Anthropic's docs, **not measured**): omp re-marks every 15th conversational user message on every request, so the prefix up to the newest anchor stays cached while the tab is used → `partial`.
- `branch`/`fork` in the same process keep the cache; a new process (`--resume`) or a `switch_session` after turns starts **cold** when a memory backend is on (the Mnemopi `<memories>` system block changes; reported upstream as omp #7196). "Open in new tab" is therefore priced as the cold price of that file's tip (the whole conversation written again).
- So a touch only counts if the tab's *current* omp process made it. `_spawnSession` stamps the registry entry's `processStartedAt` on every spawn (new tab, resume, launch restore, profile respawn; not branch/fork/`/new`, which keep the process); the hook passes it as `buildModel`'s `since`, and rows/tips whose cache comes from an earlier process carry `staleProcess` (an "earlier process" tag and a line in the detail footer).

**Actions** go through `OMP_BRIDGE.branchAt(entryId)` / `forkAt(entryId)` (`{ type: "branch" | "fork" }` via `_sendWithResponse`; both are in `ALLOWED_COMMAND_TYPES`). Rewind branches **before a user prompt**, restoring its text and images to the owning tab's composer; fork copies the prefix **through the selected message**. Both move the existing process onto a new saved file and preserve the original. `_handleResponse` resets and refetches the transcript before its id-correlated early return, including late or replayed successful responses. The tab keeps its title and last turn outcome. Actions are refused while streaming, compacting, asynchronously working or moving files; a fresh correlated `get_state` checks native settlement and queued work after admission, with submissions disabled. Native cancellation and failure remain visible. Rewind requires confirmation and explicitly does not undo workspace files. The tree pane and saved message actions use the same bridge methods; opening a file in a new tab uses `resumeSession`.

## Reported usage in chat

The **cache** disclosure under a completed assistant reply shows that request's cache-read share as recorded by omp. The existing Ambient context card shows the latest assistant request, including requests that only called tools and have no persisted chat bubble. Expand either disclosure for provider/model, reporting diagnostics, exact cache-read/write, uncached-input, total-prompt and output counts, plus omp-reported costs (which may be estimates).

This is separate from the tree's inferred reuse model above. `OMP_CACHE_USAGE` reads the [common omp usage contract](https://github.com/can1357/oh-my-pi/blob/dc6446c1/packages/catalog/src/types.ts), without a provider allowlist, and supports persisted Anthropic token fields. Prompt tokens are `input + cacheRead + cacheWrite`; output is excluded. A percentage requires every prompt component and a nonzero denominator. Missing counters remain unknown (`—`); a zero read with a positive prompt gives a `0%` recorded share. omp can [initialize unreported counters to zero](https://github.com/can1357/oh-my-pi/blob/c0d0ad76/packages/ai/test/usage-attribution.test.ts), so zero does not establish a provider's caching support or prove a provider-side cache miss. Cache activity in positive counters is evidence of recorded activity, not access to cache contents, live capacity or time remaining. Breakpoint and retention compatibility flags are not general cache-support flags.

`fromMessage` produces a request-scoped `{ provider, model, usage, source, fields }` report; `fromMessages` selects the last assistant report in transcript order. The details distinguish three boundaries:
- `omp`: recognized usage counters reached the desktop; the desktop integration is ready. Positive counters say **activity recorded**; zero or unavailable activity leaves provider support **unknown**.
- `missing`: no usable cache counters were exposed by omp. A small **cache unreported** disclosure explains that provider support is unknown; the desktop does not invent an unsupported-provider verdict or a miss.
- `unrecognized`: cache-related field names reached the desktop, but no supported counter format could be read. **cache format?** / **desktop: format gap** identify a possible integration problem. Only a bounded list of field names is retained for diagnosis, never arbitrary provider payload values; cost fields are not treated as token counters.

The bridge attaches the report on `message_end` and recovers the latest assistant report from raw `get_messages`, not timestamps or the paged display. Provider/model identify the request, never the tab's current model after a model switch. A newer assistant without usage replaces older metrics with an unavailable report. The latest result lives inside the tab's existing context snapshot, survives context refreshes and tab switches, and clears with a new conversation. The dependency-free normalizer has deterministic regression coverage; browser smoke exercises live completion, context refresh, tool-only replay, model changes, unavailable/zero/partial/unrecognized usage, legacy provider fields and native keyboard disclosure.

## Full chat history and minimap

The provider's current context is not the conversation transcript. `get_messages` may omit turns before compaction; the desktop must not discard those turns or cap its stored message array to the rendered page.

- `conversation_history` reads the active saved file off the async thread, confined to the selected profile's sessions root. It follows the selected parent chain, including pre-compaction messages and boundaries, not every branch in the file or the entire conversation family. Native `activeLeafId` overrides distinguish an absent override, an explicit empty selection and a selected ID; a dangling override uses native's last self-selected fallback. Incomplete/malformed records are skipped; duplicate IDs, missing parents and cycles fail explicitly.
- Saved messages carry persistent entry IDs for actions and keep omp's message timestamps for merging. Compaction records carry their own identity, summary, retained-entry ID and token count. The merge reconciles native context summaries (which omit `firstKeptEntryId`) with saved/live boundaries so refreshes do not duplicate them. Desktop-only rows never gain an omp message timestamp.
- Historical tool cards retain call identity and result status, but do not load large saved tool output. They say that output is unavailable; a complete live result always wins over a saved metadata-only card. Structured credential keys are redacted as in the RPC reader.
- Native image blob references are hydrated only on the selected chain. Blob reads stay in the profile's real sibling blob store, reject redirected directories/files, verify SHA-256, and respect image and total response budgets. This is required both for previewing earlier attachments and for rewinding an image-bearing prompt.
- Bounds are explicit failures, never a successful truncated history: 16 MiB per journal line, 250,000 entries, 64 MiB retained data including hydrated payloads, and 8 MiB per raw image. A failed saved read keeps available live history and exposes a Retry control. Tool output is excluded from the retained payload.
- `live.js` refreshes saved history on activation and context/history changes. Responses are scoped to tab, session file and switch generation, so a late read cannot replace another conversation. The saved history and RPC context merge into one per-tab transcript.
- `ChatView` renders a 160-item page over that complete transcript. Stable message-ID anchors keep a manually unpinned page fixed while output grows. Earlier/later pages have no gaps; minimap selection and **Your last message** select the target's page before scrolling it into view. Returning to latest resumes the live tail.
- `SessionMinimap` maps the entire transcript, not the current chat page or a recent slice. Answers use the theme accent and glow; reasoning/tool-call updates are hollow, user input neutral, and pending/completed/failed compactions labelled bands. Arrow keys and Home/End move its roving keyboard focus; Enter selects a message. Reduced motion disables minimap pulses and animated jumps.

Regression coverage: `test-conversation-navigation.mjs` exercises bridge history, compaction reconciliation and safe moves; `test-conversation-ui.mjs` exercises actual chat/action state transitions; `test-session-ui.mjs` covers targeted rewind drafts and attachments; native conversation-tree tests cover saved branches, images, bounds and path confinement.
