# Session model

One tab = one omp process. `lib.rs::setup` spawns nothing; the frontend reopens the previous run's tabs (see *Reopening tabs on relaunch*), and the session column renders `design/empty-workspace.jsx` whenever `sessions` is empty — at a launch with nothing to reopen and after the last tab closes. The welcome screen shows the start screen picked in Settings → Appearance (`startScreen`: matrix rain, latent space, next token, agent loop, forward pass or attention, each with a live preview tile) behind an ASCII-art OMP-DESKTOP logo, plus notes filed while no tab existed (`workspaceNotes`, e.g. a failed "Open with"). The canvas host is `design/backdrops/backdrop.jsx` (`window.Backdrop`: sizing, scale factor, theme tokens re-read when the root's class or style changes, offscreen-art and `env.logo` helpers from `design/backdrops/art.js`, step loop paused while the canvas is hidden or out of view — the Settings tiles behind a project tab, the empty workspace under the Settings page; its header is the renderer contract). One renderer per screen in `design/backdrops/<id>.js` registers on `window.OMP_BACKDROP_RENDERERS`; pure rules live in `app/backdrops.js` (screen list, shared math, next-token), `app/backdrops-{latent,orbit,neural,attention}.js` (`test-backdrops.mjs`) and `app/matrix-rain.js` (logo geometry, rain; `test-matrix-rain.mjs`). Each screen may draw the logo through the renderer's `logo` hook using `OMP_MATRIX.logoCells`; otherwise the host paints default glow glyphs. Renderers use theme tokens so theme or accent changes recolour the screen; under `prefers-reduced-motion` the host paints a frozen frame.
The welcome screen offers **New chat**; project folders open from the sidebar or toolbar.

Each tab also owns its **profile**: `omp --profile <id>` isolates auth/sessions/settings/caches under `~/.omp/profiles/<id>/`. The profile list lives in `<app config>/profiles.json` (`src-tauri/src/profiles.rs`); the reserved id `default` means *no* `--profile` flag, i.e. omp's own `~/.omp/agent`. Without an app config folder (`lib.rs` `config_dir`: unresolvable or relative) the list lives in memory for the app run, starting with just the built-in profile; there is deliberately no temp-dir fallback, since another account could plant a list there and pick the profile tabs start in. The same memory-only mode covers `open-tabs.json`, `recent-projects.json`, `keybindings.json`, `terminal.json`, `approval-mode.json`, `browser.json` and the `approval-rules/` grants: the app stays usable, it just remembers nothing past quitting. Rail widgets are the exception: without a config folder they are disabled (`widgets.md`), not run from memory. Ids are slugified at creation and immutable — rename changes the label only. A profile is fixed at spawn, so `OMP_BRIDGE.switchSessionProfile(id, profileId)` stops and respawns that one tab's process (its transcript is dropped with it); `saved_sessions` resolves its root per profile, so history/resume stay inside the tab's own tree. `delete_profile` only unlists — it never deletes `~/.omp/profiles/<id>/`, and `OMP_BRIDGE.deleteProfile` refuses ids still in use by an open tab (only the frontend knows the tab set).

`create_profile` also seeds `~/.omp/profiles/<id>/agent/models.yml` with a single keyless provider (`providers: {anthropic: {auth: none}}`, see `profiles::seed_bootstrap`) — RPC mode is non-interactive and omp exits at startup once no model resolves, so without the seed a fresh profile's tab would die before ever reaching `/login`. It never overwrites an existing `models.yml` (a re-created id, or a user who already wrote one, keeps theirs), and `clear_profile_bootstrap` removes it after a successful login, but only while the file is still byte-identical to what it seeded.

The same menu ticks one profile as the **startup default**, stored as `ProfilesFile::startup` — a *pointer*, not a reordering, since `normalize` pins the built-in entry first and ids are the join key for on-disk data. `None`/absent means the built-in profile. It governs any tab opened with no active tab to inherit from — including every tab at launch — and whose recent projects the empty workspace lists; `openSession` otherwise inherits the active tab's profile, and running tabs are never moved. The pointer is re-validated against the list on every load and inside every `mutate`, so deleting or hand-editing away the ticked profile degrades to the built-in one instead of dangling. `list_profiles` returns `{profiles, startupId}` in one payload so the menu can't render a checkmark against a stale default.

Corrupt profile files recover from the content-addressed snapshot ring, with the startup pointer revalidated against the recovered list. Snapshot mtimes encode write order: each is set before atomic publication and advances by at least two seconds past the previous head, preserving order across coarse filesystem clocks or wall-clock rollback without changing snapshot filenames or adding metadata sidecars. These logical mtimes can lead wall time and are not activity or retention clocks. Loading preserves the corrupt primary for inspection; only a later successful mutation quarantines and replaces it. Approval-rule recovery uses the same ordered snapshot primitive.

**History is cross-profile.** `list_saved_sessions` snapshots the configured profile list and reads each profile's sessions off the IPC thread, then sorts the combined result by last activity. Each row carries `profile_id` and `profile_name` from that registry, not from the session JSONL. The built-in profile still honours `PI_CODING_AGENT_DIR`; named profiles use their own trees. History shows and searches the profile label while keeping its recorded-cwd project filters. Browsing does not switch the active tab or top-bar profile. `resumeSession` requires the row's originating `profile_id` and reuses its saved actual cwd; the conversation-tree hook supplies its tree's profile too. Existing tabs are matched by profile and session file. A new process still passes native profile membership and resume-root validation, so an unlisted profile cannot fall back to the currently selected one.

**Composer and plan mode are per tab too** (#28), but desktop-only state omp never sees, so they live in React rather than in the bridge snapshot: `app-live.jsx` keeps a `plans` map and `design/composer.jsx` a `drafts` map (text, attachments, collapsed pastes, prompt-history recall position, in-flight image count), both keyed by session id via `app/session-ui.js` (regression `test-session-ui.mjs`) and pruned when a tab closes. Both key on `activeProject.id` (the tab being rendered, `""` with none open — a no-op key). The `Composer` deliberately stays mounted across tab switches rather than being re-keyed: a remount would re-fire its `draftInsert`/`promptInsert` effects, and an image still being prepared must land in the tab it was pasted into (`addFiles` captures the id), not in whichever tab is active when it resolves. Purely visual state (caret, slash selection, mention list) is reset on a switch instead. Plan state is not reset by `/new` or a profile respawn inside the same tab. The column beside the chat is per tab the same way (`app-live.jsx` `sides`: the rail, the conversation tree or the browser panel; `docs/architecture/browser.md`).

**Voice capture** is exclusive to the active tab. Separate composer buttons control live conversation (`/live`) and voice to text; the other button is disabled while either mode is active. Dictation uses the profile's omp STT configuration and sends `dictation_start` with a unique capture ID; `dictation_state` and full-replacement `dictation_transcript` frames update its preview. `dictation_stop` flushes and returns text, while `dictation_end` may arrive before either response and is also terminal. The bridge accepts frames only for its active capture, queues each completed transcript once with its owning tab ID, and retains the queue across React snapshot coalescing and tab switches until the composer acknowledges it. The composer appends to that still-open tab's current draft with a functional update and never recreates a closed tab. Explicit or pause-triggered stop can send the draft if **Send voice to text on stop** is enabled; bridge-initiated stops never send. If omp exits before a terminal frame, the last preview is retained with an error. The microphone spectrum and its capture lifecycle are documented in `voice-spectrum.md`; send-on-stop and auto-stop settings are in `settings.md`.

Switching tabs or opening Settings pauses live conversation and stops dictation first; closing a tab ends capture, and an omp restart stops dictation too. A failed stop leaves the microphone's tab visible. Pause uses native `live_stop` (no background audio), retains a `paused` snapshot and captions, and resumes only on an explicit action with `live_start`; it does not pretend the upstream transport survived. End closes audio without forgetting spoken history. An unexpected native end of a call that connected or resumed retains resumable history and its error; a call that never connected (e.g. omp sends `live_end` before its failed `live_start` reply without a Codex login) ends in error, not paused. Start cancellation waits for the start command's IPC handoff before sending stop, and process replacement invalidates pending replies. Voice to text and live conversation cannot run together. Regression coverage is in `test-live-voice.mjs` and `test-session-ui.mjs`. `dictation_start` first shipped in omp 18.13.2, the version floor.

Live voice meters display omp's RMS amplitudes as `20 * log10(amplitude)` dBFS on a −60 to 0 dBFS scale, with a near-full-scale warning above −6 dBFS. The UI shows bars only; numeric readings remain in the meters' screen-reader value text. Silence empties the bar; 0 dBFS fills it. This changes only the display, not microphone gain or voice detection. RMS frames carry no sample peaks, so these meters cannot diagnose clipping. Captions follow new turns and same-turn transcript updates; level-only updates do not reset their scroll position.

Each live start/resume fetches raw `get_messages`, not the desktop's paged display, then passes `OMP_LIVE_CONTEXT.instructions` as `live_start.instructions`. It preserves the native unified assistant/delegation contract and quotes visible chat text, tool results, compaction/branch summaries and earlier spoken discussion as historical data. Historical braces are escaped inside JSON strings before omp's Handlebars rendering; old template expressions cannot expand or execute. Failed history reads prevent audio startup. The complete escaped instruction template is capped at 12 KiB UTF-8, conservatively below AVAS's 16,384-token ceiling with headroom for native name expansion. Budgets include the fixed prompt, project, JSON metadata, commas and escaped Unicode/braces, not just raw history characters. Chat receives up to 8 KiB and voice up to 2 KiB of serialized rows, with a 2 Ki-character entry cap and additional byte-based truncation where needed. Saved intent, the original objective and the latest turn get reserved space so oversized anchors cannot crowd out recent discussion; omissions/truncation are explicit. Images/audio and private thinking are excluded. Captions retain at most 100 entries of 8 Ki characters; a per-call turn offset prevents native role-local turn numbers resetting on reconnect from overwriting earlier captions. Voice memory is per current conversation in an open tab: new conversation/branch/fork/profile change clears it, while same-conversation process replacement preserves it. It is not persisted across tab close or app reload. `test-live-context.mjs` covers context selection, serialized limits and template isolation.

## New-conversation workspace preparation

Fresh project opens, recent projects without an existing tab, sidebar/tab-group “new conversation”, OS folder opens and widget-created tabs enter one queued setup flow. `Start from` and `Worktree` choose the workspace; neither selection starts omp or mutates a checkout. An optional task is retained in the new tab's composer draft, never sent automatically. `Create branch for this task` is unchecked for every new conversation and requires both a task and an explicit semantic branch name. `openSession` resolves to the new tab id after confirmation, or `null` on cancellation. Task and widget inserts are queued with distinct monotonic ids until the owning draft acknowledges them, so a batched open cannot overwrite either text or insert into another tab.

If an image lightbox or file preview already owns a portal modal, setup stays queued until `#root` is no longer inert. It does not mount a competing keyboard listener or cancel the pending folder-open request when Escape dismisses the visible preview.

`conversation_workspace_inspect` returns metadata only: canonical selected and source project folders, current HEAD, local/remote branch refs and commits, and the project's saved launch defaults. It does not read the worktree index, build a file tree, walk upstream history, or acquire the workspace lifecycle guard. `conversation_workspace_status` runs a separate boolean staged/unstaged/untracked/submodule safety scan outside that guard and returns advisory ownership. The controls become available after metadata; Worktree off cannot start until status is known, while isolation can proceed without scanning source edits. Failed or missing status never means clean. Native startup repeats all applicable safety checks under the guard. No fetch runs. Detached HEAD is a single-conversation option; an unborn repository can work in place but cannot create isolation until it has a commit.

Project defaults are separate from one conversation's choices and from the profile's omp settings. The project gear saves a fully qualified base branch and Worktree flag in `<app config>/project-workspaces.json`, keyed by profile and canonical source folder. The store is memory-only without a config folder and refuses to overwrite a corrupt file. Saving changes neither files nor running conversations and starts no agent. A saved `main` + Worktree selects that branch's latest available commit for future isolated checkouts, not a persisted oid. With Worktree off, launch always initially selects the current branch; a saved base cannot silently switch the source checkout. Missing saved isolation refs stay explicit rather than selecting another branch. Defaults never store a task, new branch name or branch-creation consent.

`start_session` takes optional `workspace: {baseRef, baseCommit, worktree, acknowledgeShared, task?, branchName?}` only for a newly confirmed conversation. Rust rechecks the selected ref/commit, dirty state and tab ownership immediately before preparation. Worktree mode runs native `git worktree add --detach` unless an explicit branch name is supplied. Named creation requires a nonblank task and Worktree mode; invalid, missing or conflicting names are refused without substituting a generated name. Only private worktree directory names carry random ids. The absolute durable destination is under app data's `conversation-worktrees`; without app data it refuses isolation rather than using temporary storage. A selected repository subdirectory maps to the same relative folder in the new worktree. There is no `/wt` relocation or reliance on omp's `worktree.onStart`.

The source checkout is not stashed, cleaned, reset, force-switched or copied with its tracked/untracked edits. New isolated checkouts contain Git-tracked state, not a copy-on-write clone of ignored source data such as `target`, `node_modules` or `.env`; omp's broad ignored-file cloning is not used. Git checkout filters and post-checkout hooks still run during this explicit mutation. Failures report retained branch/folder artifacts rather than silently launching in the source checkout. Closing a successfully registered managed checkout uses the consent and recovery lifecycle below.

Native creation and in-place switching are supervised, retain only bounded diagnostic tails, have a five-minute deadline, and kill/reap their process trees on timeout, tab close, reload or shutdown cancellation. Failed operations can leave Git artifacts and are never retried automatically. The agent still starts under the conversation's resolved omp profile after workspace preparation.

With Worktree off, reusing the current branch requires explicit acknowledgement when existing changes or other tabs share the files. Changing local branches also requires a nonblank task and a clean checkout with no owning tab, including idle/background tabs and tabs using other profiles or subdirectories of that same worktree. Turning Worktree off resets the launch selection to the current branch and clears branch-creation consent. Remote-only bases require isolation. External Git processes are not locked out; revalidation detects changes it can observe but cannot prohibit an external checkout after launch.

Ownership is re-derived from the live agent and terminal folders, not a cached repository root. This protects repositories initialized around an existing conversation; unreadable ownership fails closed for in-place changes, without preventing an isolated worktree launch.

Rust's workspace manager serializes preparation, registration/spawn, respawn and final teardown. It retains ownership across `stop_session`, releases it only after `close_tab` finishes child/terminal teardown, invalidates queued admissions on webview reload, and closes admission at app shutdown. A tab close cancels that id's queued agent and terminal admissions before waiting for the lifecycle guard, without cancelling other tabs. A start already preparing settles before reload takes its tab snapshot, so it cannot finish behind cleanup as an orphan.

Ownership release is a completion barrier, not merely a queued stop: the agent tree is killed/reaped synchronously off the IPC thread; widget close is acknowledged only after its workers stop, including global plugins running in that conversation's folder; terminal spawning uses the same workspace guard so a pending shell cannot appear after its folder was released.

Every start returns `{approvalMode, path, workspace}`. `path` is the canonical actual execution folder; `workspace` holds display-only origin/base metadata, never the task or new-branch intent. The bridge adopts the returned folder before starting Git watchers or persisting the tab. Pending preparations are excluded from the saved layout. Terminal, widgets, previews, Git reads and project operations all use that binding; PR status/Auto-fix resolves the folder by conversation id in Rust, never substitutes `workspace.projectPath`. Resume and respawn do not submit new-conversation preparation again. Their native recovery layer can reconstruct a removed managed checkout before cwd validation and spawning. Explicit new-workspace requests bypass that old-checkout recovery, so invalid setup cannot restore or mutate an earlier workspace before being refused. Missing or unverifiable recovery is an error, never a fallback to the source checkout.

## Agent-driven Git feature branches

At agent startup, `agent/branch_policy.rs::for_workspace` uses gated gix discovery on the explicitly selected, resolved working folder. Only an existing Git working tree is eligible, including subfolders, unborn repositories and detached linked worktrees. Missing/empty workspaces, non-Git folders, bare repositories and discovery failures receive no branch-policy text; the app never initializes Git. `agent/spawn.rs::spawn_omp` adds `--append-system-prompt` only when that native check returns the compact `agent/branch-policy.txt`. Repository eligibility is not delegated to the model, and non-Git chats receive no “if Git” instructions. Context/Evidence extensions, project instructions, approvals and the browser-only config overlay remain unchanged; no RPC or stored-workspace schema changes are needed.

Normal chat setup does not require a task or branch name. An isolated checkout still starts detached when no explicit branch was selected. After the first task prompt, the agent creates and checks out an ordinary local branch before implementation, choosing a concise name from the task and repository conventions rather than a session id or timestamp. Related follow-ups stay on that branch; a separate feature can create another. Resume, restart and restore are not new-feature requests.

Explicit Git instructions win: an exact name, prefix, base, an existing branch, or “do not create a branch.” The optional setup controls remain an explicit user choice, not a prerequisite. Automatic branching preserves existing changes and never force-switches, resets, discards, stashes, commits, pushes or creates another worktree. The agent confirms the branch before editing and stops if a safe switch cannot be made.

Eligibility is deterministic Rust code; task intent, naming and ordinary Git tool calls remain agent-driven. The existing HEAD watcher updates the branch display. Tabs sharing one physical folder share its branch and files. No branch-naming state is duplicated in React, `live.js`, or a desktop store. Filesystem regressions cover the eligibility boundaries, and a real compiled-startup probe verifies the policy's presence/absence in omp's resolved `get_state.systemPrompt`, followed by a first-task branch and runtime assertions.

## Disposable conversation worktrees

Closing a native-verified, app-managed linked checkout offers **Cancel**, **Keep for now**, or **Save restore point and remove**. Normal project tabs still close without making their folders disposable. Legacy managed checkouts are adopted when opened; an arbitrary directory name is not removal authority. Native linked-worktree metadata, source identity and backlinks must agree. Failed starts, reload teardown and app shutdown retain files without inventing a Keep decision.

The native lifecycle guard serializes close/removal against preparation, registration and terminal spawning. A destructive close rejects other owning tabs or shells, stops this tab's agent, browser, widgets and terminal, and only then captures and verifies a restore point. Capture or verification failure retains the checkout and visible tab with an actionable error; the stopped agent is not presented as still running. Keep remains available as a safe retry. An interrupted removal retains its committed restore point and any remaining files rather than recapturing a partial checkout.

The private app-data `worktree-storage` directory holds the durable catalog, consent/activity clocks, conversation/profile aliases and immutable `snapshots`. Native session JSONL and its Evidence ledger stay in the profile's session store; imported Evidence assets stay in their own app-data store. Neither depends on the disposable conversation directory. Snapshot storage can contain secrets such as environment files and databases; it is private local storage, not an encrypted or off-device backup.

On Windows, the storage root is created with an explicit current-user owner and protected private DACL before generic directory validation. Elevated processes must not create it first with an inherited Administrators owner. Existing roots owned by another principal still fail closed; this initialization does not take ownership of them or rewrite descendant ACLs.

A restore point owns its Git objects in a verified bundle, the saved commit and branch metadata, staged index state, working files, untracked files and ignored local data. Only the disclosed `node_modules/`, `target/`, `.next/` and `.turbo/` cache paths may be omitted, and only when Git-ignored and containing no tracked files. Unknown ignored folders are retained. Supported permissions, ownership, symlinks, extended attributes and ACLs are verified; unsupported data, special files, read errors or failed metadata verification block removal instead of silently dropping data.

Reopening imports the saved objects even if source garbage collection removed that commit. Detached checkouts remain detached and create no branch. Named checkouts reuse the saved branch only if its tip still matches and it is available; moved, occupied or deleted branches restore detached instead of generating an opaque recovery branch or resetting an existing branch. An occupied old destination is left untouched and a fresh managed directory is used. The source repository must still exist with its verified identity; missing or changed source identity retains the restore point and reports an error. Failed restoration retains partial files and never overwrites them on retry.

**Keep for now** grants a thirty-day inactivity lease, measured from the later of the Keep decision and last explicit conversation use. Explicit history reopen, tab selection, prompt/steer/follow-up submission, question response and Settings restore record activity. Passive app startup, automatic checkout reconstruction, replay, metadata polling and unattended PR remediation do not renew it. Reconstruction preserves the original Keep clock; explicit use updates the separate activity clock. A native worker checks after sixty seconds at startup and hourly thereafter while the app runs.

Every automatic candidate is rechecked under the lifecycle guard. Open app conversations, their registered shells and pinned worktrees are protected, including background tabs. Only an expired Keep lease authorizes automatic snapshot-and-removal, with the same verification as explicit removal. Background scans never infer consent for an unleased checkout. External editors and processes are not locked out; pin a checkout used outside the app and stop external writers before explicit removal.

**Settings → Session → Workspace storage** exposes inventory, pinning, restoration, size refresh and an explicit due-worktree check. Default advisory budgets are fifteen retained checkouts and 20 GiB of measured checkout data; restore-point sizes are reported separately and restore points are not automatically deleted. Budget pressure never shortens a lease or overrides ownership/pinning. Unknown or failed measurements remain explicit, and stale measurements cannot be applied to a different restored generation. Storage corruption, changed directory identity or failed catalog writes refuse cleanup rather than falling back to temporary storage.

Pure state/policy and real Git/filesystem regressions cover commit/index/file recovery, source GC, destination collisions, metadata preservation/refusal, aliases, lease boundaries, pinning, transactional failure and stale measurements. Native smoke exercises actual close choices, failed capture/Keep retry, remove/reopen and retention with isolated synthetic repositories and transcripts; platform-specific runtime limitations must remain explicit in its evidence.

## Conversation evidence

Evidence belongs to the native omp conversation, not the visible tab or the todo list. The desktop-supplied `evidence` extension identifies the profile and session and restores the latest `omp-desktop:evidence` custom entry on the active session branch. Mutations append a versioned snapshot and flush it to the native session JSONL; branching, switching and reopening restore that branch's state rather than a global frontend cache. Missing persistence or invalid saved metadata is reported, not overwritten. The UI can show an unpinned policy warning if the initial snapshot could not be saved.

An outcome describes intended work and may carry optional textual todo references; each outcome owns its criteria. The user can add or edit outcomes and criteria, including required/pinned criteria, and can take ownership of an agent proposal. The agent may propose its own outcomes and criteria, but cannot edit user-owned ones. Records link to an outcome and optionally a criterion, identify their author/source, result, summary and limitations, and may reference a file, URL, imported artifact, CI snapshot or execution receipt. Optional bounded `finding.expected` and `finding.observed` strings describe the behavioral comparison; optional `reviewRequested` explicitly asks for human judgment. Both survive CI capture and native session restore. A receipt is an observed execution with error/exit information and bounded output, not an interpretation. Only the user can review records, waive/unwaive criteria, retire entries, change policy or control collection. Rejection, waiver and retirement preserve reasons and audit history; agents cannot make those decisions for user-owned work.

Freshness compares the record's source fingerprint and criterion revision with the current source, including HEAD and the dirty-worktree digest. Receipt-linked records also compare the before-execution fingerprint. Changed criteria or source, incomplete fingerprints and unavailable source state are stale or unknown, not passes. Failed, blocked/cancelled, missing and stale proof remains explicit; a later pass does not erase an unresolved failure. A rejected capture remains inspectable, and without applicable replacement proof its reason remains a goal gap rather than falling back silently to a weaker observation. User review is separate: collection creates no review obligation, an explicit request remains unaccepted until a user decision, and historical acceptance never refreshes source freshness. Captured GitHub PR check state refers to the reported source commit, not uncommitted changes; absent, pending and unknown checks are not a pass.

The shared native preset library is stored in `<app config>/evidence-presets.json`; without an app config folder it is memory-only, and an unreadable library refuses writes. Built-in **Standard** is read-only; users can create, duplicate, edit and delete custom presets. A source-project default overrides the global default, which overrides Standard. Worktree conversations use their source project for this lookup. At initialization the resolved policy, including its revision and prompts, is pinned in the conversation's native ledger. Changing library entries or defaults does not retroactively alter an existing snapshot; explicitly applying a saved preset, an available revision update or the inherited default changes that conversation. Preset actions use saved values, not unsaved editor drafts.

The extension hooks native lifecycle, tool and stop events. When collection is enabled, before-work and before-handoff guidance use the pinned policy; after a source change or an edit/write tool result the post-change trigger supplies collection guidance. Tool receipts and fingerprints are captured independently of card visibility. The default handoff is advisory; the user may select a single bounded follow-up in a preset. That stop hook attempts continuation only for missing, failed or known-stale gaps and does not waive, accept or silently resolve them. Collection can be switched off separately from hiding the Ambient card. A saved evidence request is ledger data only; the explicit send action asks the agent, rather than automatically dispatching saved requests.

Artifact import copies regular files into private `<app data>/evidence/assets` storage; agent imports pass through a per-run private inbox. Content is validated from bytes and hashed, with no arbitrary filesystem path exposed to the webview. Supported imports are UTF-8 text up to 1 MiB, PNG/JPEG/GIF/WebP images up to 8 MiB, and MP4/WebM video up to 64 MiB. WebM must declare a video track; HTML, SVG, other binary formats and audio-only files are unsupported. Text preview is bounded to 128 KiB; the asset store is capped at 1 GiB and 8,192 entries. The `evidence:` protocol serves authorized artifacts through revocable run-scoped capability tokens, checks integrity, and supports bounded video byte ranges; playback depends on webview codec support. No private storage means imports are unavailable. The feature imports available files; it does not promise screenshot capture, video recording, CI access or independent verification where those capabilities are absent.

The default Proof view groups current evidence by goal and applicable criterion, not execution count. It shows expected/observed findings, strongest proof, coverage and gaps, with provenance/logs behind disclosures. Demonstration requires current inspectable support and a reported behavioral pass; file/URL references and executions without captured output remain supporting details. Screenshots enlarge and compare, videos use native playback/seeking controls, and text output is readable inline. UI-discovered media failures live in conversation-owner-scoped hook state shared across panels; explicit Refresh increments the load generation and preserves a gap until a successful read/decode. Native membership, capability and integrity checks remain authoritative. **Remove from scope** retires an item without deleting its records; **Accept exception** waives an unmet criterion without turning it into demonstrated behavior. Both expose reasons, confirmation and retained history; **Remove exception** reverses a waiver, while retirement has no restore operation.

Rust's `evidence` host owns the preset store, source fingerprints, PR-check lookup, artifact storage, private host requests, capability protocol and per-run snapshots. The native extension runtime and ledger own branch-scoped operations, persistence and hooks; the agent bridge intercepts its private transport rather than displaying it as chat. The shared `evidence-model` projects collection statuses and reports in extension/frontend, while `evidence-proof` projects the frontend's goal-oriented behavioral proof separately. The `evidence-client` and `use-evidence` hook communicate with native state; the hook owns conversation-scoped operations and artifact-load state. Evidence JSX owns inspector/card interaction and drafts, never the ledger or user decisions.

## Repository-free chats

**New chat** starts the same ordinary omp RPC session as a project tab, under the inherited/startup profile, without a folder picker. Each chat gets its own empty workspace in the durable app-data directory, under `chats/workspaces/<opaque-id>`; metadata lives separately under `chats/metadata`. No Git repository, checkout, dependency installation, or template is created. Directories are private (`0700` on Unix), never a shared temporary folder or disposable cache. Creation fails explicitly if durable storage is unavailable.

The sidebar separates **Chats** from **Projects**. Closed chats remain listed for the active profile; open chats from other profiles remain visible and carry profile badges. `scratchId` identifies the chat's metadata independently of the ephemeral tab id and persists with the open-tab layout. Titles and the profile-owned omp session file are saved on changes, with serialized writes; a session path that omp has announced but not written is retried rather than treated as durable history. `/new` starts fresh history within the same workspace. Profile selection works on an empty workspace and on a running chat. Switching profiles retains the workspace files without copying them: a profile alias shares the workspace and logical chat group, but owns its own title and session file. A new profile starts fresh; switching back resumes that profile's retained conversation. An already-open profile variant is focused rather than duplicated. Auth, model configuration and conversation history remain profile-owned. Separately reopened older history uses a distinct chat group while sharing existing workspace files.

**Manage workspace** lists regular files, exports an individual file with a native save dialog, and shows workspace-content bytes and file count. Existing destinations are never overwritten. Inspection is on demand, capped at 20,000 entries and 64 directory levels; an incomplete size is labelled "At least", and incomplete file lists are errors rather than silently truncated lists. Symlinks and special files are excluded from measurement; export cannot traverse links, and promotion refuses them rather than silently dropping files. These are workspace-content sizes, not allocated disk blocks, omp history, model caches, or total app storage. There is no filesystem quota: an agent or terminal can still create large files/dependency trees.

**Promote to project** opens the native destination picker before changing the chat, so canceling preserves the exact tab identity, draft, attachments and plan state. After a selection, work must be idle and voice capture stopped. The bridge obtains a full native `fork` snapshot with a new UUID, then stops the owning tab's omp/browser/terminal before copying. The registry id stays present throughout temporary shutdown and restart, preserving tab-local state. The destination must be a new, non-existing project folder; a failed copy removes its partial destination. A single-use backend receipt binds history migration to that destination. Native `session pack`/`session unpack --cwd` relocates the **disposable fork**, never the only original: unpack replaces same-UUID local copies, and a bare `--resume --cwd` does not update history's persisted working directory. The backend checks the fork's parent identity and artifact parity. Archives use a private transfer directory and are removed after the operation. The project opens under the original profile with the migrated snapshot history. On error the original chat is restored under the same tab id; a previously closed chat opened only to take the snapshot is closed again. After copy/migration/startup failure, a destination or snapshot may remain for recovery; errors identify a retained snapshot when applicable. Pack/unpack availability at the current version floor is unproven; an unsupported command fails visibly, leaving the original history intact.

**Retention and storage:** closing a tab does not delete files or history. Successful promotion retains the original workspace and its original conversation as a recovery copy; the project owns a separately identified snapshot, so reopening the source cannot take ownership of project history. Delete that copy explicitly when no longer needed. Deletion requires a closed chat and a second confirmation. It removes that metadata entry, and removes files only when no other chat/profile references the workspace. Physical removal/promotion refuses any registered tab rooted at or below the workspace, including another profile or an ordinary folder tab. Interrupted deletion is retryable and does not hide unrelated chats. Omp history is never deleted: resuming history whose private workspace was deleted creates an empty replacement workspace, not a reconstruction of deleted files. There is no age/count-based eviction of user files, automatic compression, repository duplication, or background recursive size scan. Forking and native transfer temporarily duplicate history/artifacts, so promotion requires additional disk space; original history remains available even if it fails.

The lifecycle borrows [JetBrains scratch files](https://www.jetbrains.com/help/idea/scratches.html)' project-independent storage and explicit move/export concept, and [VS Code untitled workspaces](https://code.visualstudio.com/docs/editing/workspaces/workspaces)' explicit keep/discard decision. [Cursor's worktree cleanup](https://cursor.com/docs/configuration/worktrees) documents machine-wide count-based eviction; that policy is deliberately not applied to scratch files, which may be the only copy of user work.

Regression coverage: `test-scratch-chats.mjs` exercises public bridge ownership, close/reopen, busy guards, promotion recovery and metadata ordering; `test-chat-workspace.mjs` covers file actions, confirmation, errors and keyboard dismissal; the backend scratch module tests persistence, containment, copying, measurement and native transfer failures.
