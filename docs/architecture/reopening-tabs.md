# Reopening tabs on relaunch (#17)

`live.js` keeps `<app config>/open-tabs.json` (`src-tauri/src/open_tabs.rs`, commands `open_tabs_load`/`open_tabs_save`) equal to the open tabs: each tab's folder, profile, conversation `.jsonl` and label, in tab order — `sessionRegistry` order, which a drag or keyboard move rearranges (#40, see `project-navigation.md`) — plus the active index. The shape and the restore arguments are pure helpers in `project-nav.js` (`tabLayout`, `restoreSpec`, regression `test-project-nav.mjs`).

An optional `workspace` field records the selected source project, base ref/commit and isolation flag. It is descriptive, not new-conversation preparation. The saved actual `path` is used when present; a durable conversation/profile recovery binding can reconstruct a removed managed checkout before native cwd validation. The returned canonical folder replaces the old path in the tab and saved layout. Neither a missing checkout nor recovery failure permits launching in the source folder. Existing intact layouts without metadata retain their meaning.

Before registration, `normalizeWorkspaces` flattens old origin chains (a worktree created from another worktree) to a known source project and normalizes generated default labels while retaining meaningful titles. A metadata-only Git lookup can repair a linked checkout's origin via its common repository directory. If no origin can be recovered, the persisted source identity is retained. This normalization changes presentation/grouping only; any replacement execution folder comes from the verified native recovery lifecycle, not from substituting a source project or requesting fresh conversation setup.

- **Written continuously, never on quit**: `notify()` → `_persistLayout` compares `tabLayout`'s JSON with the last write and writes on change — one write at a time, latest wins (`_flushLayout`), so the file ends at the newest layout and layouts superseded mid-write are skipped. The updater's installer launch, a relaunch and an OS shutdown end the app without the webview getting a say.
- **Disarmed until the startup restore settled** (`_layoutArmed`): before that the registry lacks the saved tabs, and a write would replace the file with a partial set. When the tabs are exactly what the restore registered, arming *adopts* that layout as already written, so tabs that failed to reopen stay in the file until the first real change — a launch where omp cannot start at all (#34) does not wipe the saved tabs. A tab the user opened, closed or picked during the restore is a real change: `_layoutKey` is left unset and the arming `notify` writes it.
- Startup order: `_refreshProfiles` → `_restoreOpenTabs` → `_setupExternalOpens`. A cold-start "Open with" opens after the restored tabs and ends up active.
- **Settings → Session "Reopen tabs on launch"** (`restoreTabs`, default on; `docs/architecture/settings.md`), read from the stored tweaks at `live.js` load (`OMP_TWEAKS_STORE`), so the boot restore sees it before React mounts. Off: `_restoreOpenTabs` opens nothing and never calls `open_tabs_load`; the file is left untouched, since arming adopts the empty layout as already written, and is first rewritten at the first real tab change.
- `_restoreOpenTabs` spawns tabs one at a time via `_startProjectSession(…, {activate: false, remember: false})` — no activation round-trips per tab, no reordering of recent projects. Starts and activations are passive (`userInitiated: false`) and do not renew workspace inactivity, even when native recovery reconstructs a missing checkout. Activation is decided after each spawn against the then-active tab; a tab the user opened or picked meanwhile keeps focus. A failed activation is logged and the loop goes on.
- `open_tabs_load` filters ordinary project tabs against the file system and durable recovery catalog: a gone folder is retained only when its saved conversation has a native recovery binding; otherwise it is skipped with a note. A gone conversation file can reopen as a fresh tab only on an intact folder; a pathless project tab without a conversation is dropped. Resume paths remain validated against the originating profile, and restoration verifies its checkpoint and source identity before omp starts. See [Disposable conversation worktrees](session-model.md#disposable-conversation-worktrees).
- Repository-free chats also persist `scratchId` and remain eligible even if their saved path is stale or empty. Restore resolves that identity against Rust-owned chat metadata and uses its workspace path, not the saved layout's path; a missing identity is an error. An empty chat keeps its label even without a conversation file. Closing a chat removes its tab from this layout but leaves it reopenable from Chats; see `session-model.md`.
- **No config folder, no file**: when the app config folder can't be resolved, the layout is kept in memory (`OpenTabsStore`'s `config_file::ConfigFile` holds the bytes the file would, so a webview reload still restores through the same `restorable` filter) and the next launch starts with no tabs. There is deliberately no temp-dir fallback: a planted `open-tabs.json` there would choose the folders, profiles and conversations omp starts in.
- Tab ids are `session-<ms>` from a monotonic counter (`_lastSessionMs`): back-to-back restores can start within one millisecond.
- **Unanswered questions** are recovered from the resumed process's raw entries and active leaf, not from its filtered `get_messages` history or the old process's volatile request ids. A restored ask remains answerable; its answer continues the conversation as a new user reply without replaying tools. See `ask-dialog.md` for eligibility, cancellation persistence and limits.

## Transcript reconstruction

On activation, the bridge merges the active saved conversation's history with current RPC context. `conversation_history` follows the active parent chain through pre-compaction turns and compaction boundaries, without treating abandoned branches as chat. Raw `get_entries` also recovers rich tool cards and unanswered questions from the active leaf; native context-inventory records remain rail-only. Activation, file and session guards reject stale responses.

`adaptAgentMessages` pairs assistant `toolCall` blocks with `toolResult` messages by call id, preserving invocation order, arguments, intent and available saved results. It reuses `buildToolStartCard` / `finalizeToolCard`, so restored chat cards and minimap cells share the live tool classification. Historical metadata-only cards explicitly identify unavailable output; finished live cards retain richer streamed data, timing and UI identity. Persisted results can finish cards whose end frames were missed. Restoring executes no tool and sends no agent prompt.

The complete recovered transcript remains in per-tab state. Chat renders bounded pages of 160 items without discarding earlier messages, and the minimap covers the complete transcript. Desktop-only approval/retry bookkeeping remains memory-only; this is reconstruction from omp's saved messages, not a second transcript store. See [Full chat history and minimap](conversation-tree.md#full-chat-history-and-minimap).

Coverage: `test-transcript-restore.mjs` exercises rich output, failures, call/completion order, repeated refreshes, missed end frames and active ancestry. `test-ask-recovery.mjs` exercises reopening questions with tool history absent from model context and rail-only native observations. `test-conversation-navigation.mjs` covers saved history and paging.
